# Architecture

Generated by `react-ts-project-scaffold`. New features must be created with the `react-ts-feature-builder` skill.

## Enabled modules

- **Routing**: TanStack Router (file-based, flat dot-notation filenames)
- **API**: TanStack Query + HTTP client — base URL from `VITE_API_URL`, Bearer/refresh-token headers read from the persisted `auth` slice
- **Global state**: `useReducer` + `Context` persisted in `localStorage` — slices: `auth`, `cart`

## Pages

### Storefront (phase 1) — public + client, mounted under the pathless `_storefront` layout route (no URL prefix)

- `HomePage` → `/` — catalog, category filter, search, sort
- `ProductDetailPage` → `/product/$idProduct`
- `LoginPage` → `/login`
- `RegisterPage` → `/register`
- `CheckoutPage` → `/checkout` (auth required) — address + shipment method, creates the pre-order
- `CheckoutPaymentPage` → `/checkout/payment` (auth required) — simulated card, no API call; confirms the real shipment after "payment"
- `OrdersPage` → `/orders` (auth required)
- `OrderDetailPage` → `/orders/$idInvoice` (auth required)

### Admin (phase 2) — role `ADPRU`, mounted under the real `admin` segment layout route

- `AdminDashboardPage` → `/admin` — reuses `GET /api/common/dashboard` (shared with Operator)
- `AdminProductsPage` → `/admin/products` — list (reuses the public `GET /api/common/product`, there is no separate admin list endpoint), search, delete
- `AdminProductFormPage` → `/admin/products/new` and `/admin/products/$idProduct` — create/edit a product with its variants and per-variant photo upload (S3 presigned URLs)
- `AdminCuponsPage` → `/admin/cupons` — list + create/edit (Drawer) + delete
- `AdminProductTypesPage` → `/admin/product-types` — list + create/edit (Drawer) + delete
- `AdminUsersPage` → `/admin/users` — list + search + status filter + inactivate + create account with role (`POST /api/auth/account/privado`)

### Operator (phase 3) — role `OPPRU`, mounted under the real `operator` segment layout route

- `OperatorDashboardPage` → `/operator` — same dashboard data as Admin
- `OperatorInventoryPage` → `/operator/inventory` — adjust stock by SKU (`sumar`/`restar`); there is no inventory-read endpoint, so it reuses the public product list to show current quantities
- `OperatorShipmentsPage` → `/operator/shipments` — list confirmed shipments, filter by status, advance shipment status (requires a delivery guide only on the first transition)

### Image uploads (Admin only)

The frontend builds the S3 key — the backend never generates or expects a specific prefix. Convention used here: `product/{SKU}/{timestamp}-{sanitized-filename}`. Flow: `POST /api/admin/stored-file` to get a presigned URL per file → direct `PUT` to that URL with the raw file (outside the `http` client, different host, no JSON envelope) → the returned key is sent back as `s3BucketKey` on the variant. Only `image/jpeg`, `image/png`, `image/webp` up to 5 MB are accepted (`core/utils/productImage.ts`) — this is the single standard image format enforced across the whole storefront (`ProductImage`, square frame, used in grid/detail/cart/checkout/admin table).

### Simulated payment

`CheckoutPaymentPage` (phase 1) validates a fake card (number/name/expiry/CVV) entirely client-side with no network call; only after that client-side "approval" does it call the real backend to confirm the shipment (`PATCH /api/client/shippment/:id`). No payment gateway exists or is called anywhere.

Route files use flat dot-notation (`_storefront.checkout.payment.tsx`) instead of folders, matching the single-file style already used by `__root.tsx`. `_storefront.tsx` is a **pathless** layout route (TanStack Router's `_` prefix strips the segment from the URL) that mounts `StorefrontLayout` at `/`. `admin.tsx` and `operator.tsx` are **real** path-segment layout routes (no underscore) so their children sit under `/admin/*` and `/operator/*` — a pathless layout cannot coexist with another pathless layout that also resolves its index to `/`, which is why these two use a real segment instead of the `_storefront` pattern.

### Deep imports inside `hooks/`

`.oxlintrc.json` restricts `@hooks/*` deep imports even between hook domains (e.g. `hooks/admin` reading `hooks/common`) — unlike `components`, `services` and `store`, the `hooks` override carves out no exception. Cross-domain reads (e.g. `adminKeys` invalidating `commonKeys.products()`, or an admin page-hook reusing `useCatalogQuery`) go through the root `@hooks` barrel, not a deep path. This is safe in practice (the referenced exports are only read inside function bodies invoked after the whole module graph settles, never at module-eval time) but is a stricter rule than the prose in this file implied before phase 2 — followed literally per the linter, which is the enforced source of truth.

## Layer dependency rules

Dependencies point downward only:

```
app → routes → pages → layouts → components → core / styles
                 │         │
                 └─────────┴──→ hooks → services → core
                           └──→ store → core
```

- `components`: pure UI, controlled by props; imports only `@core` utils and `@styles`; never `@hooks`, `@store`, `@services`, `@pages`, `@layouts`, `@tanstack/*`.
- `services` / `store` / `core`: no React UI; never import `@components`, `@pages`, `@layouts`, `@hooks`.
- Cross-layer imports go through the layer barrel (e.g. `@components`). A deep alias (`@components/Icon`) is only used inside the same layer. No `../` imports (the sole exception is `app/router.ts` importing the generated `../routeTree.gen`, which lives outside every layer).

## Aliases

`@app`, `@assets`, `@components`, `@core`, `@hooks`, `@layouts`, `@pages`, `@services`, `@store`, `@styles` — configured in `tsconfig.app.json` and `vite.config.ts` for every allowed layer, even ones with no folder yet.

## Barrels

Every layer folder (except `styles` and `assets`, imported by file) has an `index.ts` re-exporting its public API. Add new units to the nearest barrel in the same change that creates them.
